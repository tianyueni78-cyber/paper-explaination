# 时间顺序工作流成果文件要求

## 1. 目录结构

每个P节点建立一个独立文件夹，依次命名为`P01`、`P02`、……、`P11`。

每个清单条目对应一份独立Markdown成果文件，命名格式为：

```text
三位新序号_验收事项名称.md
```

例如：

```text
P01/001_研究背景与应用场景.md
P01/002_研究范围与不研究的内容.md
```

## 2. 文件内容

成果文件直接呈现该事项的具体内容，使读者不依赖聊天记录或验收表也能理解本阶段形成了什么。

正文可按事项需要包含定义、对象、组成部分、流程、参数、公式、表格、案例、结果或结论。内容组织服从事项本身，不套用统一空模板。

## 3. 不写入成果正文的内容

- 验收标准、通过条件和勾选说明；
- “从旧文件迁移”“原来属于某阶段”等管理过程；
- 为证明合规而写的反向辩解；
- 与事项内容无关的工作汇报；
- 只有标题、状态或链接而没有实质内容的占位文字。

上述管理信息只放在总清单、节点结论或进度记录中。

## 4. 清单与成果的关系

- 清单中的每个新序号链接到对应成果文件；
- 成果文件没有具体内容时，该项不能勾选；
- 多个原ID确属同一成果时可以共用一份文件，但清单必须明确共同指向；
- 后续修改成果内容时直接更新该文件，并在节点结论中记录影响。

## 5. 节点通过后的学习建议

节点通过后另行给出能力学习建议，说明可迁移能力、就业用途、自然语言编码环境下的学习价值、建议掌握深度和最小练习。学习建议不写入单项成果正文，也不作为科研验收依据。

## 6. 每个节点采用双Skill分工

每个P节点开始前，从当前已安装Skill和`Supervisor-Skills`仓库中选择两类职责不同的Skill：

1. **执行Skill**：理解本节点任务，制定节点内部计划，完成清单事项并生成对应成果文件；
2. **验收Skill**：在成果完成后独立检查内容、证据、代码或实验是否满足本节点要求，并给出通过、退回或证据不足结论。

执行Skill和验收Skill不能因为名称相近而合并为一次自我确认。验收必须在成果形成后单独进行，并留下验收记录。

## 7. 成果生成与验收的关系

生成`.md`成果文件表示该项已经形成可验收对象，**不自动表示该项通过**。

单项通过需要同时满足：

1. 执行Skill完成对应具体成果；
2. 成果文件不是空壳或占位文本；
3. 验收Skill完成独立检查；
4. 检查使用了与事项相符的证据；
5. 验收记录明确写出“通过”。

节点通过需要本节点所有必需项通过、条件项通过或有依据地标记不适用，并生成节点结论文档。

## 8. 涉及代码时的附加交付

清单事项涉及代码时，不能只提交代码说明文档。对应成果至少包括：

- 实际源代码或配置文件；
- 代码功能与调用方式的Markdown说明；
- 对应测试代码；
- 实际运行命令；
- 测试或运行结果记录；
- 代码版本或Git提交；
- 影响算法行为时的baseline隔离与差异说明。

代码、测试和运行记录通过验收后，相关清单项才能勾选。
