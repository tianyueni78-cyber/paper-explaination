# 创新点最低成本验证协议

## 1. 验证目标

在正式实现完整 Q-learning 前，用少量固定样本回答四个问题：

1. 不同调度状态是否确实适合不同局部动作？
2. 瓶颈感知区域是否比同规模随机区域更有效？
3. 自适应选择动作的潜在收益是否高于固定选择？
4. 诊断与调度开销是否小到值得加入算法？

该探针只决定 **Go / Revise / Stop**，不能替代正式论文实验。

## 2. 启动前提
- baseline 相关代码保持不变；
- 固定一组可复现的小实例和随机种子；
- 固定同一解码器、目标函数、动态事件和锁定规则；
- 记录机器、Python/MATLAB版本和计时方式；
- 预先写下样本选择、动作集合和判断阈值，禁止看结果后挑样本。

若 decoder parity 尚未通过，允许先搭建脚本接口，但不得据此作创新有效性结论。

## 3. 最小目录与文件

正式开始探针时，在独立创新工作区创建：

```text
experiments/probes/
├─ probe_config.yaml
├─ export_states.py
├─ evaluate_actions.py
└─ analyze_oracle.py
innovation/
├─ bottleneck_features.py
└─ region_builder.py
outputs/probes/<run_id>/
├─ sampled_states.jsonl
├─ action_results.csv
├─ summary.csv
└─ figures/
```

若当前 baseline 主体仍是 MATLAB，可先用 MATLAB 导出固定状态，再用 Python 做特征、汇总和分析；不要为了探针提前重写整个 baseline。

## 4. 具体执行动作

### 步骤 0：冻结探针配置

在 `probe_config.yaml` 中填写：

- 2–3 个小规模实例；
- 3–5 个预先指定种子；
- 至少一种机器故障和一种 AGV 故障状态；
- 每个动作的统一时间上限；
- 小/中区域规模定义；
- 固定动作集合；
- Go / Stop 阈值。

输出：一份可重复执行的配置文件。

你重点负责：为什么选这些状态、预算和阈值。

### 步骤 1：抽取 baseline 状态

运行 baseline，在初始化后、正常搜索中段、搜索停滞期和动态事件后各抽取若干候选解。每个样本保存：

- 原始染色体及必要资源状态；
- Makespan、TEC、非支配等级；
- machineTable、AGVTable、充电/电量、工序起止时间；
- 事件类型、已完成/执行中/未开始集合；
- 实例、种子、代数或时间戳。

输出：`sampled_states.jsonl`。

验收：同一样本重新载入并解码，目标值在容差内一致。

### 步骤 2：实现瓶颈特征

在 `bottleneck_features.py` 中先实现最少特征：

- 机器累计负载、利用率或关键完工贡献；
- AGV等待/运输负载、空驶或阻塞贡献；
- 事件影响规模；
- 最近若干次评价无改进次数；
- 剩余预算比例。

输出：每个样本的瓶颈资源、瓶颈类型及原始数值，不只输出标签。

验收：随机抽取 5–10 个样本，对照甘特图或表格人工解释结果。

你重点负责：指标定义、单位、阈值和解释；AI可辅助文件读取与测试脚手架。

### 步骤 3：生成合法局部区域

在 `region_builder.py` 中实现：

- 瓶颈感知小区域；
- 瓶颈感知中区域；
- 与二者规模相同的随机对照区域。

区域必须排除已完成/不可移动任务，并继承在制任务、故障资源、AGV位置、电量与可用时间。

验收：每类事件至少检查 10 个区域；非法区域必须在执行邻域前被拒绝并记录原因。

### 步骤 4：穷举少量候选动作

在 `evaluate_actions.py` 中，对每个固定样本执行 4–6 个候选动作。建议第一版动作只组合：

- 小/中范围；
- 工序顺序、机器、AGV或机器–AGV协调邻域；
- 短/长两个离散时间配额。

每次动作从同一原始样本独立开始，记录：

- 动作及区域；
- 原/新 Makespan、TEC；
- 是否可行、是否支配原解；
- HV或档案质量增量；
- 诊断耗时、搜索耗时、完整评价次数；
- 无改进、异常和超时原因。

输出：`action_results.csv`。

验收：相同配置和种子可重复生成一致或可解释的随机结果。

### 步骤 5：做“事后最优动作”分析

`analyze_oracle.py` 对每个样本选出事后收益最高的动作，比较：

- Oracle：每个状态事后选最佳动作；
- Best-fixed：所有状态永远使用整体平均最好的动作；
- Random：随机动作；
- Bottleneck-region 与同规模 Random-region。

这一步不训练 Q-learning。它先判断“状态自适应选择”是否存在值得学习的信号。

输出：`summary.csv` 和最少三张图：动作胜率、单位时间收益、区域策略对比。

### 步骤 6：Go / Revise / Stop

建议判断规则：

**Go**：

- 接受进入评价的候选解 100% 可合法解码，非法候选能被安全拒绝；
- 不同状态下的最佳动作存在明显差异，而非一个动作几乎全胜；
- Oracle 的单位时间收益稳定优于 Best-fixed 和 Random；
- 瓶颈感知区域在多数实例/种子上优于同规模随机区域；
- 诊断与区域生成开销未吞噬主要搜索预算。

**Revise**：有动作差异，但特征无法解释或非法率/开销偏高。优先缩小状态与动作集合，不立即升级强化学习模型。

**Stop**：

- 一个固定动作在几乎所有状态中最好；
- Oracle 相对 Best-fixed 没有实质收益；
- 瓶颈区域不优于随机区域；
- 大量区域无法合法解码；
- 诊断开销超过潜在改进。

“实质收益”的数值阈值在步骤 0 根据 baseline 波动和单次预算预注册，不能在看到结果后决定。

## 5. 通过探针后的最小实现顺序

1. 先实现可解释规则控制器，验证状态到动作的接口；
2. 再接入表格 Q-learning，沿用原更新机制；
3. 加入硬预算管理和超时回退；
4. 进行 B0–B4 消融；
5. 最后才扩大实例、事件和独立运行次数。

如果规则控制器已经达到 Oracle 可实现上界附近，应重新评估 Q-learning 是否必要。

## 6. 正式实验的公平性底线

- 主实验：相同墙钟时间预算；
- 补充实验：相同完整解码/目标评价次数；
- 相同实例、种子策略、运行次数和参考前沿构建方式；
- 报告全部预注册运行，不挑最好结果；
- 同时报告质量、时间、可行率和稳定性；
- baseline 与创新算法都调用冻结的同一解码器。

## 7. 能力训练分工

你应亲自负责或主导：

1. 把瓶颈、停滞、预算写成可计算定义；
2. 设计状态、动作和奖励，并解释每个选择；
3. 规定合法解锁边界和测试反例；
4. 预注册实验与 Go / Stop 标准；
5. 阅读结果、定位失败原因并形成业务式结论。

可让 AI 重点辅助：

- 数据读写、批量运行、日志和绘图脚手架；
- 单元测试模板与重复代码；
- 文献检索表和实验结果整理；
- 在你给出公式和接口后完成受控实现。

这样实际训练到的就业技能是：资源状态诊断、容量/预算分配、SQL/Python式数据分析思维、实验设计、指标体系和把算法结果转成决策建议，而不只是“让 AI 写一个优化器”。

## 8. 探针结论模板

完成后只用下列格式做决策：

```text
结论：Go / Revise / Stop
证据：Oracle vs Best-fixed；Bottleneck vs Random；开销；非法率
适用范围：实例、事件、预算
失败案例：哪些状态无效，为什么
下一步：唯一的最小改动
```

在完成这一页之前，不扩展求解器修复、深度强化学习、预测模型或新动态场景。
